# PR - 2025-12-27: DataSourceRef Candidates Feature

## Summary

This PR adds a new `candidates` parameter to the `DataSourceRef` attribute, enabling discriminator-based data source selection similar to `PropertyCandidates`.

---

## Feature: DataSourceRef Candidates

### Problem
Previously, selecting a data source dynamically based on runtime conditions (e.g., feature flags, context values) was not possible. Users had to choose between:
- `id` (single source, optionally with `fallbacks`)
- `providers` (aggregation from multiple sources)

Neither approach allowed conditional source selection based on expressions.

### Solution
Added a `candidates` parameter that accepts an array of candidate definitions. Each candidate has:
- `id` (required): The data source ID to use if elected
- `discriminator` (required): An expression that must evaluate to `true` for the candidate to be elected
- `priority` (optional): Overrides the base priority if this candidate is elected

The first candidate whose discriminator evaluates to `true` is elected.

### Usage
```php
#[DataSourcesStore([
    new MultiPropDataSource(id: 'newFeatureSource', class: NewFeatureSource::class, method: 'getData'),
    new MultiPropDataSource(id: 'oldFeatureSource', class: OldFeatureSource::class, method: 'getData'),
])]
class User
{
    #[DataSourceRef(
        candidates: [
            ['id' => 'newFeatureSource', 'discriminator' => "expr(context('new_feature_enabled'))", 'priority' => 15],
            ['id' => 'oldFeatureSource', 'discriminator' => 'expr(true)'],
        ],
        priority: 10
    )]
    private ?string $name = null;
}
```

### Priority Resolution
- If the elected candidate defines a `priority`, it takes precedence over the base `priority`
- Example: base priority is 10, but elected candidate has priority 15 → effective priority is 15

   - `"DataSourceRef: id and providers are mutually exclusive"` → `"DataSourceRef: id, providers, and candidates are mutually exclusive"`

---

## Validation Rules (Updated)

| Rule | Description |
|------|-------------|
| Mutual exclusivity | `id`, `providers`, and `candidates` cannot be used together |
| `fallbacks` requires `id` | Fallbacks can only be used with `id` mode |
| `exceptionOnNoValidDataSource` requires `fallbacks` | Exception handling requires fallbacks |
| Candidate structure | Each candidate must have `id` and `discriminator` keys |

---

## Lineage Collection

When lineage collection is enabled, candidate resolution events are recorded with:
- `type`: `candidate_resolution`
- `originalValue`: All candidates that were evaluated
- `finalValue`: The elected candidate (or null if none matched)
- `reason`: `candidate_elected` or `no_candidate_matched`
- `metadata`:
  - `basePriority`: The priority defined at attribute level
  - `effectivePriority`: The actual priority used (candidate's or base)
  - `candidatesCount`: Number of candidates evaluated
  - `electedCandidatePriority`: The elected candidate's priority (if defined)
